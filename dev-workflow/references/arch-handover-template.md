# 技术架构交接文档集模板

> 场景 E（arch-handover.md）使用。文档集建议位于 `docs/architecture/`，由 README 导航 + 7 个分册组成。
> 规则：分册可裁剪（删除需用户确认）；格式统一用 Mermaid 图 + Markdown 表格；所有事实必须来自真实项目材料，缺失标注 `【待确认】`。

## README 导航模板（docs/architecture/README.md）

```
# <产品名> 技术架构交接文档集

> 用途：让不熟悉本产品的人员与 AI 快速、全面了解产品的技术、逻辑与方向。
> 维护：随代码变更联动更新（影响映射表见附录）。最后更新：YYYY-MM-DD。

## 分册导航

| 分册 | 内容 | 适合谁 |
|---|---|---|
| 01 产品概览与演进方向 | 产品是什么、边界、端侧与角色 | 所有人 |
| 02 技术架构 | 技术栈、架构图、模块边界、调用链 | 开发 / AI |
| 03 业务逻辑与核心流程 | 核心业务规则与流程 | 产品 / 开发 / AI |

| 05 部署运维 | 环境、配置、发布、监控、备份 | 运维 / 开发 |

## 快速定位总表

## 各分册章节要点

### 01 产品概览与演进方向

- 产品定位与用户角色；端侧形态（Web / H5 / 小程序 / OpenAPI）；
- 核心功能清单（表格：模块 | 功能 | 说明）；
- 当前阶段与关键指标（如有）。

### 02 技术架构

- **技术栈版本表**（层 | 技术 | 版本 | 用途）；
- **架构全景图**：按 C4 分层绘制（规范见 `references/diagrams.md`）——L1 系统上下文图 + L2 容器图（客户端 → 网关 → 应用 → 存储 → 外部依赖）必画，L3 组件图按需；Mermaid C4 语法为主，复杂部署图用 PlantUML 备选；图源文件落盘 `docs/architecture/diagrams/` 并登记图清单表；
- **代码结构**：目录树 + 每个目录职责注释，标注关键模块入口文件路径；
- **模块边界与调用链**：模块清单表（模块 | 职责 | 依赖 | 关键文件）；
- 关键技术机制（认证、权限、缓存、消息、任务调度等，各一段 + 关键代码位置）。

### 03 业务逻辑与核心流程

- 核心业务流程 3–5 个（Mermaid 流程图，编号步骤描述）；
- 状态机与约束规则（状态转换路径、删除约束、不变量）；
- 业务规则清单（表格：规则 | 实现位置 | 说明）。

### 04 数据模型

- ER 图（Mermaid `erDiagram`）；
- 核心表清单（表 | 用途 | 关键字段 | 对应实体文件）；
- 缓存结构（key 格式、过期策略、失效时机）；
- 数据初始化与迁移（初始化脚本、迁移工具）。

### 05 部署运维

- 环境清单（环境 | 地址 | 配置差异）；
- 部署拓扑与依赖中间件（版本、端口、账号体系说明）；
- 发布流程（构建 → 部署 → 验证 → 回滚步骤）；
- 监控与告警（指标、日志位置、告警通道）；
- 备份与恢复（备份策略、恢复步骤）。

### 06 已知问题、技术债与坑

- 已知问题清单（问题 | 影响 | 临时规避 | 状态）；
- 技术债清单（债 | 位置 | 偿还建议 | 优先级）；
- 历史事故摘要（指向复盘记录）；
- 注意事项（容易踩的坑：时区、精度、编码、限流等）。

### 07 演进方向与路线

- 产品方向：规划中的功能与目标；
- 技术方向：计划中的重构、架构升级、技术债偿还顺序；
- 二期预留：数据库预留字段、接口预留、扩展点；
- 路线图（时间轴 | 目标 | 内容）。

| docker-compose.yml | 05 部署运维 §部署拓扑 | 部署配置变更 |
| ... | ... | ... |
```

> 规则：A/B/C 场景每次变更完成后，按本表查找受影响章节并联动更新；找不到对应项时向用户确认是否需要新增映射。联动对象包括：受影响分册章节、图清单表中的关联图（`docs/architecture/diagrams/`）、`.devflow/agents/` 中的角色知识文件——文档、图、知识三者一起保鲜。
