# 自我审查闸门与规格审查维度清单（跨场景支持手册）

> 本手册在总纲（SKILL.md）底线之上执行。定位：它是「自我审查闸门」的执行细则与「规格审查维度清单」的唯一来源——场景 A/B/C/D/E/F/G 在关键交付点前、场景 H（spec-review.md）在逐维审查时均引用本手册。
> 机制：自我审查是**同一执行者对照规格自查**，**不替代**跨角色沟通评审（agents.md）与用户确认。顺序恒为：自我审查 → 跨角色评审 → 用户确认。

## 一、定位与触发时机

任何方案、代码、问题清单、设计/交接文档、测试计划、复盘报告，在**提交用户或宣布完成前**，执行者须对照「规格 / 检查清单」自我审查一次；发现偏差、遗漏或未确认项，先修正或标注，再交付。

| 场景 | 交付点（自我审查时机） | 审查对象 vs 规格基准 |
|---|---|---|
| A 新功能开发 | 阶段 3 方案输出后；阶段 7 完成前 | 方案 vs 需求规格；实现 vs 方案 + 规格 |
| B 单点修 bug | 第 3 步方案后；第 6 步完成前 | 修复方案 vs 根因；修复 vs 原 bug 场景 |
| C 全量排查 | 阶段 3 问题清单后；阶段 6 报告前 | 问题清单 vs 代码证据；报告 vs 修复清单 |
| D 设计方案 | 第 5 步一致性自检时 | 设计文档 vs 需求 / 现状材料 |
| E 架构交接 | 第 6 步一致性自检时 | 交接文档 vs 真实代码 / 配置 |
| F 自动化测试 | 测试计划确认后；用例交付前 | 用例 vs 规格验收点 |
| G 回顾性 | 报告交付前 | 结论 vs 真实材料（UPDATE_LOG / git / 测试记录） |
| H 规格审查 | 逐维审查时 | 规格文档 / 实现 vs 审查维度清单 |

## 二、可配置审查维度清单

按对象三类裁剪；无对应材料时标注 `【待确认】`，禁止编造。

### 1. 需求规格（PRD / 用户故事 / 验收标准）

- **完整性**：目标、边界、端侧 / 角色、非功能指标、异常流、验收标准是否齐全；
- **一致性**：术语 / 角色 / 权限 / 指标前后一致；与既有系统约定一致；
- **歧义性**：模糊表述（"尽量 / 适当 / 合理"）、无量化指标、隐含假设未说明；
- **可测性**：每条需求有可验证的验收标准；可复现 / 可自动化；
- **可行性**：技术可行、资源 / 时间约束、依赖就绪度。

### 2. 技术规格 · 接口契约 · 数据模型

- **契约一致性**：字段名 / 类型 / 枚举 / 错误码 / 时间金额格式前后端一致；文档 vs 类型定义 vs Mock 一致；
- **版本与兼容**：版本前缀、破坏性变更识别、向后兼容；
- **数据模型一致**：ER 图 vs 表结构 vs 接口出入参 vs 脱敏规则一致。

### 3. 实现 vs 规格

- **满足度**：实现覆盖规格全部要点；无遗漏 / 偏差 / 过度实现（越界）；
- **边界与异常**：规格中的边界 / 异常 / 约束在实现中落实；
- **文档同步**：注释 / 接口文档 / README / 交接文档与实现一致。

## 三、自我审查流程

1. 明确审查对象与规格基准（本次交付什么、对照什么规格）；
2. 从维度清单按对象裁剪出本次适用维度；
3. 逐维走查（基于证据，引用文件 / 行号 / 出处）；
4. 输出自审报告（见第四节）；
5. 偏差 / 遗漏 / 待确认项：可自行修正的在交付前修正；需用户裁决的标注后随交付一并提交；
6. 结论「可交付」才进入下一闸门（跨角色评审 → 用户确认）。

## 四、自审报告模板

```
## 自我审查报告
- 审查对象：<方案 / 代码 / 问题清单 / 文档 / 测试 / 复盘报告>
- 规格基准：<需求 / 契约 / 设计文档 / 真实材料>
- 逐维结论：
| 维度 | 结论（通过 / 偏差 / 待确认） | 证据 / 位置 | 说明 |
|---|---|---|---|
| ... | ... | ... | ... |
- 偏差与待确认清单：<编号列出>
- 修正动作：<已修正 / 待用户裁决>
- 结论：可交付 / 需返工
```

## 五、自检清单

- [ ] 已明确审查对象与规格基准
- [ ] 已按对象裁剪适用维度，逐维走查，结论有证据
- [ ] 偏差 / 遗漏 / 待确认项已修正或标注，未带着未确认项交付
- [ ] 自我审查先于跨角色评审与用户确认，未以自审替代它们
