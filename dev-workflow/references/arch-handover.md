# 场景 E：技术架构交接文档工作流

> 本手册在总纲（SKILL.md）底线之上执行：确认闸门、基于证据（禁止编造）、提问规范均按总纲执行，本手册不再重复展开。
> 定位：对**既有产品**做现状盘点 + 演进方向梳理，产出面向**接手人员与 AI** 的交接文档集——让不熟悉该产品的人与 AI 都能全面、细致地了解产品的技术、逻辑、方向。与场景 D（前瞻型设计方案）互补：D 面向"未来要建成什么样"，E 面向"现在是什么样、为什么是这样、往哪走"。

【强制工作流，任何步骤不得跳过】文档正文在用户确认前不得展开；缺失信息向用户提问或标注 `【待确认】`，不允许臆造填充。

## 第 1 步：确认盘点范围

与用户确认以下内容（编号一次问全）：

1. 盘点范围：全产品 / 指定模块；
2. 分册取舍：模板共 7 册（见 `references/arch-handover-template.md`），不适用或暂不需要的分册可裁剪，删除需用户确认；
3. 深度：面向新成员上手（粗）还是面向深度维护（细，含关键代码位置）；
4. 是否包含「演进方向与路线」（产品 / 技术方向、二期预留）；
5. 产出位置与形态：文档集目录（建议 `docs/architecture/`）+ README 导航；
6. 是否建立「影响映射表」以支持后续变更自动联动保鲜（强烈建议建立）。

## 第 2 步：信息采集

按以下来源采集，**结论必须来自真实材料**，每条关键事实尽量落到出处：

- 代码结构：目录树、模块边界、技术栈版本（`package.json` / `pom.xml` / `go.mod` / `requirements.txt` 等）；
- 配置与部署：`docker-compose.yml`、CI 配置、环境变量、Nginx / 网关配置、发布流程；
- 数据层：数据库 schema、ORM 实体、缓存结构、初始化脚本；
- 接口清单：路由 / 控制器 / API 文档；
- 历史上下文：`UPDATE_LOG.md`、git 提交历史、旧版设计文档（场景 D 产出）、README；
- 无代码可读时：向用户询问系统现状、技术栈、核心业务、模块划分、部署方式、已知痛点。

## 第 3 步：输出文档集大纲并确认

- 按 `references/arch-handover-template.md` 生成文档集大纲：README 导航 + 各分册的章节骨架，每章附一句话说明"本章将写什么"；
- 标注无法从现有材料获证的内容为 `【待确认】`，汇总清单一并提交；
- **输出大纲后停止，等待用户确认或调整，确认后才展开正文。**

## 第 4 步：逐册生成正文

- 严格按确认后的大纲展开，格式要求遵循模板（图表、Markdown 表格、代码位置引用）；
- **图表按 `references/diagrams.md` 执行**：现状架构图按 C4 分层（L1 Context + L2 Container 必画，L3 Component 按需；Mermaid C4 语法为主，复杂部署图用 PlantUML 备选），ER 图用 `erDiagram`，时序 / 流程用 `sequenceDiagram` / `flowchart`；图源文件落盘 `docs/architecture/diagrams/` 并登记图清单表；
- 技术栈、版本号、端口、账号体系等事实必须与真实项目一致；不确定的标注 `【待确认】`；
- 篇幅较大时分批生成（如每次 1–2 册），每批完成后简要小结进度。

## 第 5 步：AI 可检索性设计（每册必做）

交接文档同时服务人与 AI，每册必须包含：

- **快速定位表**：主题 / 问题 → 章节 / 关键文件路径，让 AI 后续会话能一次命中目标章节；
- **关键事实索引**：技术栈版本表、模块清单表、接口清单表、数据库表清单等结构化表格（AI 检索的第一入口）；
- **图清单表**：`docs/architecture/diagrams/README.md`（图表规范见 `references/diagrams.md`），README 导航中链接，供 AI 快速定位已有图与源文件；
- 术语表（附录）：产品特有名词与代码内名称的对应关系。

## 第 6 步：一致性自检与交付

- [ ] README 导航与各分册实际章节一致
- [ ] 各分册间的事实（技术栈、模块名、表名、接口路径）互相一致
- [ ] 全部 `【待确认】` 项已汇总列出，提醒用户逐项落实
- [ ] 每册都有快速定位表与关键事实索引

一致性自检后，再对照真实代码 / 配置 / 材料做一次自我审查（见 `references/self-review.md`），确认文档事实与现状一致、无编造与遗漏。

交付后：

- 在项目 `UPDATE_LOG.md` 记录：文档集位置、覆盖范围、待确认项数量；
- **建立影响映射表**（模板见 `references/arch-handover-template.md` 附录）：分册章节 ↔ 代码路径 / 模块的对应关系，供 A/B/C 变更完成后联动更新（总纲「交接文档保鲜联动规范」）。

## 更新既有交接文档集时

- 先通读旧文档集与影响映射表，以**增量修订**方式进行，不推翻未变更章节；
- 每册头部维护修订历史（版本 | 日期 | 修订内容 | 来源），本次更新新增一行；
- 被替换的旧内容在对应章节注明变更原因（一句话即可）。

## 自检清单

- [ ] 盘点范围、分册取舍、深度、演进方向、落点已与用户确认
- [ ] 关键事实均来自真实材料或用户答复，`【待确认】` 项已汇总
- [ ] 大纲经用户确认后才展开正文；分批生成时每批有小结
- [ ] 架构图 / ER 图 / 表格格式符合模板；各册事实互相一致
- [ ] 每册具备快速定位表 + 关键事实索引；术语表完整
- [ ] 已写入 UPDATE_LOG；影响映射表已建立
