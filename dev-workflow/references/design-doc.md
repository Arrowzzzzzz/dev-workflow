# 场景 D：系统总体设计方案生成

> 本手册在总纲（SKILL.md）底线之上执行：确认闸门、基于证据（禁止编造）、提问规范均按总纲执行，本手册不再重复展开。文档确认通过后进入实施阶段时，切换到场景 A（new-feature.md）流程执行。与本场景并列的「现状盘点 / 交接」类文档走场景 E（arch-handover.md）。

按标准模板为系统更新、重构或新建项目生成《总体设计方案》文档。产出的文档应作为开发、测试、运维的唯一依据——新成员阅读后可直接参与开发。

文档语言默认中文。章节骨架与各章编写要求见 `references/design-doc-template.md`,生成正文前必须先阅读该文件。

## 核心原则

1. **禁止编造**:技术栈、版本号、表结构、接口、配置等必须来源于真实项目信息(代码、文档、用户输入)。信息缺失时向用户提问或显式标注 `【待确认】`,不允许臆造填充。
2. **先确认、后产出**:大纲未经用户确认前,不得展开正文。
3. **一致性优先**:权限标识、错误码、表字段、接口路径在全文各章节间必须互相一致。

## 工作流程

### 第 1 步:理解现状

- 若在代码仓库环境中:阅读项目结构、关键配置文件(如 `pom.xml`/`package.json`/`docker-compose.yml`)、已有设计文档、`UPDATE_LOG.md`,梳理出当前技术栈、模块边界、数据模型与已知痛点。
- 若无代码可读:向用户询问系统现状、技术栈、核心业务、本次更新动机。
- 整理为一份简短的《现状摘要》呈现给用户,标注不确定项。

### 第 2 步:确认范围

与用户确认以下内容后再继续:

- 本次建设目标与痛点(为什么要更新)
- 一期范围 / 二期预留的边界
- 系统端侧(Web 管理后台、H5、OpenAPI 等)与角色划分
- 非功能性指标是否有明确要求(性能、可用性、安全)

### 第 3 步:输出大纲并等待确认

- 按 `references/design-doc-template.md` 的章节骨架生成大纲,每章附一句话说明"本章将写什么"。
- 结合项目实际裁剪:不适用的章节(如无国际化需求)标注"本项目不适用,建议删除",由用户决定去留。
- **输出大纲后停止,等待用户确认或调整,确认后才展开正文。**

### 第 4 步:逐章生成正文

- 严格按确认后的大纲展开,格式要求(表格结构、图表、代码示例位置)遵循模板文件中各章的编写要点。
- **图表绘制遵循 `references/diagrams.md`**:架构图按 C4 分层(Mermaid C4 语法为主,复杂部署图用 PlantUML 备选),ER 图用 Mermaid `erDiagram`,图源文件按规范落盘并登记图清单表;功能清单、权限矩阵、表结构、错误码使用 Markdown 表格。
- 代码示例必须基于项目实际技术栈编写;若技术栈未定,给出选型建议并标注 `【待确认】`。
- 文档篇幅较长时可分批生成(如每次 3–5 章),每批完成后简要小结进度。

### 第 5 步:一致性自检

正文完成后逐项检查:

- [ ] 功能模块清单中的权限标识与"权限与安全设计"、接口文档章节一致
- [ ] 错误码在"错误码规范"与各业务流程描述中一致
- [ ] 数据库表字段与 ER 图、接口出入参、脱敏规则一致
- [ ] 接口路径、版本前缀(如 `/api/v1`)全文统一
- [ ] 文档概述中的修订历史已包含本次版本,版本号正确递增
- [ ] 所有 `【待确认】` 项已汇总列出,提醒用户逐项落实

一致性自检后，再对照需求 / 现状材料做一次自我审查（见 `references/self-review.md`），确认设计文档与规格一致、无编造与遗漏。

### 第 6 步:交付与记录

- 默认输出为 Markdown 文件,文件名格式:`《<系统名>总体设计方案》v<版本号>.md`。
- 若项目维护 `UPDATE_LOG.md`,在其中追加一条记录:日期、文档版本、本次设计方案覆盖范围、待确认项数量,保持 AI 会话上下文连续性(模板见 `assets/UPDATE_LOG.md`)。
- 若项目已有交接文档集(场景 E 产出),按影响映射表登记本设计文档相关章节 ↔ 代码 / 模块的对应关系,供后续变更联动保鲜。

## 更新既有设计方案时

若项目已存在旧版设计方案:

- 先通读旧版,变更以**增量修订**方式进行,不推翻未变更章节。
- 修订历史表中新增一行,写明本次修订内容。
- 对被替换的旧方案内容,在对应章节注明变更原因(一句话即可)。
