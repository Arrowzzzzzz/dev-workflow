# 场景 C：全量排查修复工作流

> 本手册在总纲（SKILL.md）底线之上执行：确认闸门、基于证据、实施纪律、高风险二次确认、测试失败修正规则、回归测试硬门禁、自测规范均按总纲执行，本手册不再重复展开。
> 边界：本场景面向**系统性排查**（用户未指出具体问题）。用户已指出具体 bug / 报错 → 场景 B（bug-fix.md）。逐项修复时，每个问题的修复动作按场景 B 的第 3–5 步执行（方案 → 跨角色沟通评审 → 确认 → 回归验证）；执行角色按 `references/agents.md` 依问题归属分配，实施时加载 `references/coding-standards.md`。

## 你的角色与核心目标

你是一名代码审查与缺陷修复助手，负责对项目前后端代码进行系统性排查。**核心目标：发现代码中的 Bug，并在获得用户确认后进行修复**，确保系统功能正确、稳定运行。

这里有一条贯穿始终、不可让步的底线：**未经用户明确确认，不得修改任何一行代码。** 之所以如此严格，是因为代码修改是有副作用的操作——一次自作主张的改动可能引入新问题、破坏用户有意为之的设计、或改动用户并不想动的地方。把"发现问题"和"动手修改"两个阶段用一道确认闸门隔开，能让用户始终掌握控制权，也让每次改动都是双方共识的结果。

整体流程如下：

> 理解上下文 → 系统排查 → 输出问题清单 → **（停下）交互确认** → 实施修复 → 修复报告与验证 → 写入更新记录

## 一、排查范围与检测重点（11 大维度）

排查覆盖以下 11 个维度。实际项目按技术栈裁剪，但不要因为「看起来没问题」就整类跳过——每个维度都要实际走查后再下结论。发现问题要基于代码证据（具体文件与行号），不凭印象猜测。

### 1. 前端展示与交互
- **页面展示**：渲染错误、数据未回显 / 回显错误、样式错乱与布局溢出、空状态 / 加载态 / 错误态缺失、列表 key 缺失或不唯一导致的渲染异常
- **按钮与交互**：点击无响应、可重复提交（未防抖节流 / 未禁用按钮）、事件绑定或解绑错误、事件冒泡 / 默认行为处理不当
- **表单与校验**：前端校验缺失或规则错误、校验与后端不一致、必填 / 格式 / 长度 / 联动校验遗漏、错误提示不明确
- **状态管理**：状态未更新 / 未重置、组件间数据不同步、路由切换后残留旧数据、全局状态被意外污染
- **前端资源泄漏**：监听器 / 定时器 / 订阅未销毁、闭包引用导致的内存泄漏

### 2. 交互与视觉设计走查

这一维度关注的不是「功能是否报错」，而是「实现出来的界面与交互是否达到设计与可用性标准」。这类问题通常不抛异常、测试也不会失败，却直接影响用户能否顺利完成任务，且极易在多人协作、多轮迭代后悄悄劣化，因此需要独立走查而不能并入功能排查。

- **设计还原度与视觉一致性**：与设计稿 / 设计规范（design tokens）的偏差——间距、圆角、阴影、字号字重、行高、色值硬编码而未走变量；同类元素在不同页面样式不统一；组件库已有样式却另起炉灶重写
- **布局与排版**：对齐与栅格错位、间距节奏混乱、内容溢出 / 截断 / 换行异常（长文本、长单词、超长数字、无空格串）、图片比例失真、z-index 混乱导致遮挡、CSS 选择器优先级冲突互相覆盖（尤其是区块间 margin / padding 被意外抵消）
- **响应式与多端适配**：断点表现异常、移动端小屏布局塌陷、横竖屏切换、超宽屏留白失控、浏览器缩放与系统大字号下布局破损、刘海屏 / 底部指示条等安全区域未处理
- **交互状态完整性**：hover / focus / active / disabled / selected / loading / 错误 等状态缺失或不可辨；可点击元素无光标与视觉反馈；触摸目标过小（建议 ≥ 44×44px）；禁用态仅变灰但仍可点击
- **反馈与过渡**：关键操作后无反馈（提交、保存、复制、删除）、加载无骨架屏或进度提示、动效缺失或过度（时长不当、无 `prefers-reduced-motion` 降级）、状态切换生硬导致用户不确定是否成功
- **信息层级与可读性**：视觉重心不清、主次按钮层级颠倒（危险操作被做成主按钮）、文本对比度不足、长内容缺少分组与留白、关键信息被弱化
- **空状态与异常态设计**：空列表、无搜索结果、加载失败、无权限、网络离线等场景缺少专门设计，或只有一句提示而没有引导下一步的操作入口——空屏应当是一个行动邀请，而不是死胡同
- **文案与措辞（微文案）**：按钮未用主动语态说明结果（用「保存修改」而非「提交」）、同一动作在流程中前后改名（点「发布」却提示「已提交」）、术语不一致或暴露系统实现（说「Webhook 配置」而非用户认知里的「通知」）、报错只说出错不说如何解决或直接抛技术错误码、国际化文案未翻译 / 截断 / 变量拼接语序错误
- **交互流程顺畅度**：关键路径步骤冗余、缺少默认值与快捷方式、破坏性操作（删除 / 清空 / 不可逆提交）缺少二次确认或撤销、表单校验不定位到出错字段、长表单无草稿保存、错误后用户已填内容被清空
- **无障碍（a11y）**：正文对比度低于 4.5:1、仅靠颜色传达信息（如只用红绿区分状态）、图片缺 alt、表单控件缺关联 label、键盘不可达 / Tab 顺序混乱 / 焦点样式被 `outline: none` 抹掉、缺少必要的 ARIA 角色与状态、动态内容更新未通知读屏软件

**走查这一维度时的分寸**：这里必须区分「客观缺陷」与「审美取向」，否则容易把用户有意为之的设计当成 Bug 改掉。对比度不达标、键盘不可达、焦点不可见、触摸目标过小、内容溢出、破坏性操作无确认、文案自相矛盾——这些有明确标准或会真实阻碍用户，按缺陷上报；而配色偏好、圆角大小、动效风格、排版气质属于用户的决策范围，作为「建议」提出并标注为主观项，交给用户定夺。判断准绳的优先级是：项目设计稿 / 设计规范 / 组件库 > 平台惯例与无障碍标准 > 同一产品内是否自洽一致。若项目没有任何设计规范，就以「一致性」和「可用性」为主要依据，不要以个人审美代替用户决策。

### 3. 接口调用与前后端通信
- **请求侧**：参数字段名 / 类型 / 必填项与后端契约不一致、缺少必要请求头或鉴权 token、URL / method 使用错误
- **响应侧**：未处理非 2xx 状态码、未做空值 / 异常结构 / 空数组判断、错误信息未反馈给用户、超时与重试策略缺失
- **异步与并发**：竞态条件（后发先至覆盖数据）、未捕获的 Promise rejection、重复并发请求、请求未取消（组件卸载后仍 setState）
- **契约一致性（前后端交叉比对）**：字段命名、数据类型、枚举值、时间 / 金额 / 分页格式在前后端是否一致；接口文档 / 类型定义 / Mock 与实际实现是否一致

### 4. 后端业务逻辑
- **业务规则**：条件判断错误、逻辑运算符误用（`&&` / `||`、`==` / `===`）、状态流转错误、业务规则实现与需求不符
- **边界条件**：空集合 / null / 0 / 负数 / 极大值 / 超长输入 / 特殊字符处理遗漏、循环边界（off-by-one）、除零
- **数据处理**：空指针 / 空值访问、类型转换与精度错误（浮点、大整数、金额）、时区 / 日期处理错误、编码问题
- **入参校验**：服务端入参校验缺失或不足、未做白名单 / 范围校验、过度信任前端传参

### 5. 数据与持久层
- **查询正确性**：SQL / ORM 查询逻辑错误、关联 / 分组 / 排序错误、条件遗漏导致的多查 / 漏查
- **事务与一致性**：事务边界错误、该加事务未加、异常时未回滚、跨服务操作缺乏最终一致性保障
- **ORM 与缓存**：懒加载 / N+1、脏数据、缓存与数据库不一致、缓存击穿 / 穿透 / 雪崩、缓存失效策略缺失
- **数据完整性**：唯一约束 / 外键 / 非空约束缺失、脏写 / 重复写入、软删除与查询未配合

### 6. 安全漏洞（重点维度）
- **注入类**：SQL / NoSQL 注入（字符串拼接 SQL）、命令注入、模板注入（SSTI）、LDAP / XPath 注入
- **前端注入与跨站**：XSS（存储型 / 反射型 / DOM 型，危险 sink 如 `innerHTML` / `eval` / `document.write`）、CSRF（缺少 token / SameSite）、点击劫持（缺少 `X-Frame-Options` / CSP）
- **服务端请求与解析**：SSRF（用户可控 URL 外发请求）、XXE（XML 外部实体）、不安全的反序列化、路径遍历 / 任意文件读取、文件上传校验缺失（类型 / 大小 / 落地路径 / 可执行）
- **认证**：弱口令策略、认证绕过、会话固定、token / JWT 处理不当（`alg:none`、未校验签名、未设过期）、密码重置流程可绕过
- **授权**：越权访问（IDOR，直接改 ID 查他人数据）、水平 / 垂直权限提升、缺失接口级权限校验、前端隐藏但后端未拦截
- **敏感信息**：硬编码密钥 / 密码 / token、密码明文或弱哈希存储、敏感数据打进日志 / 响应 / URL 参数、错误堆栈暴露给用户
- **配置类**：CORS 配置过宽（`*` + 携带凭证）、安全响应头缺失（HSTS / CSP / X-Content-Type-Options）、调试接口 / 默认账号 / 目录列举暴露

### 7. 可靠性与健壮性
- **异常处理**：异常未捕获或被静默吞掉（空 catch）、捕获范围过宽掩盖真实错误、异常后状态不一致、错误未向上传递
- **并发安全**：竞态条件、死锁、共享可变状态未加锁、非线程安全对象在多线程使用、幂等性缺失导致重复处理
- **资源管理**：数据库连接 / 文件句柄 / 网络连接 / 流未关闭、连接池耗尽、内存泄漏、大对象未释放
- **容错与降级**：外部依赖失败无降级 / 熔断、无超时导致级联阻塞、缺少重试或重试无退避

### 8. 性能与资源效率
- **后端性能**：N+1 查询、慢查询 / 缺索引、全表扫描、大结果集无分页、循环内查库 / 调接口、重复计算、锁粒度过大
- **前端性能**：不必要的重渲染、大列表未虚拟化、包体积过大 / 未按需加载、重复请求、大图 / 大资源未优化
- **通用**：算法复杂度过高、频繁 GC、阻塞主线程 / 事件循环、日志或序列化开销过大

### 9. 配置、环境与依赖
- **配置管理**：硬编码环境相关配置（域名 / 端口 / 路径）、多环境配置混用、配置项缺失或默认值不安全
- **密钥与凭证**：密钥 / 证书 / 连接串写死在代码或提交到仓库、密钥未走密钥管理
- **构建与部署**：构建配置错误、环境变量缺失、产物包含调试代码 / source map、依赖未锁版本
- **第三方依赖**：已知漏洞依赖（可提示做 SCA 扫描）、版本冲突、废弃 / 不再维护的库、使用已弃用 API

### 10. 代码质量与可维护性
- **冲突与残留**：合并冲突标记（`<<<<<<<` / `=======` / `>>>>>>>`）、临时调试代码（`console.log` / 断点 / 测试桩）
- **冗余与死代码**：未使用的变量 / 函数 / 导入 / 组件 / 依赖、不可达代码、大段被注释的废弃代码、重复代码块
- **可读性**：命名不清或误导、超长函数 / 高圈复杂度、魔法数字 / 硬编码字面量、嵌套过深
- **日志质量**：关键路径无日志难以排障、日志过多产生噪声、日志级别使用不当、日志含敏感信息（与安全维度联动）

### 11. 兼容性、测试与文档
- **兼容性**：浏览器 / 设备 / 分辨率兼容、API 版本兼容与向后兼容、数据库 / 依赖版本兼容
- **测试覆盖**：核心逻辑缺少测试、测试失效或被跳过（`skip` / 注释）、测试与实现不符
- **文档一致性**：注释 / 接口文档 / README 与代码实现不符或已过时（仅作提示，非强制修复项）

## 二、修复实践流程（六阶段）

### 阶段 1：理解上下文
- 先浏览项目结构，明确技术栈、模块划分、前后端交互方式与构建配置。
- 阅读与排查目标相关的业务逻辑，先弄清「代码应该做什么」，再对照「实际做了什么」——很多"疑似 Bug"其实是没读懂意图。
- 业务意图不明确时，先向用户提问，不做主观臆断。

### 阶段 2：系统排查与根因定位
- 按模块逐一排查，并对前后端接口契约做交叉比对。
- 每个疑似问题都追溯到根因（root cause），不停留在表面现象——修表象往往按下葫芦浮起瓢。
- 严格区分两类结论，这个区分很重要，因为把猜测当结论直接改会误伤正确代码：
  - **确定的 Bug**：有明确证据（逻辑矛盾、必然报错、契约不一致）。
  - **疑似问题**：可能是有意设计或缺少上下文，必须标注「疑似」并向用户求证。

### 阶段 3：输出结构化问题清单（然后停下）
每个问题按以下字段报告，让用户能快速判断、按编号处置：

| 字段 | 说明 |
|---|---|
| 编号 | 如 #1、#2，供用户按编号指定处理 |
| 严重程度 | P0 / P1 / P2 / P3 |
| 位置 | 文件路径 + 行号 / 函数名 |
| 问题描述 | 现象 + 触发条件 |
| 根因分析 | 为什么会出问题 |
| 修复方案 | 改哪里、怎么改、影响范围 |
| 风险提示 | 修复可能带来的副作用（如有） |

**严重程度分级标准：**

| 级别 | 定义 | 示例 |
|---|---|---|
| P0 致命 | 崩溃、数据丢失 / 错乱、高危安全漏洞 | SQL 注入、越权访问他人数据、硬编码密钥泄露、空指针导致服务不可用 |
| P1 严重 | 核心功能不可用、业务结果错误、明显性能 / 可靠性缺陷 | 订单金额算错、提交接口必然失败、N+1 拖垮接口、异常被静默吞掉 |
| P2 一般 | 交互异常、边界场景出错、一般安全 / 健壮性问题、阻碍使用的体验缺陷 | 按钮可重复提交、空列表页面报错、CORS 配置过宽、资源未关闭、键盘不可达、对比度不达标、删除操作无二次确认 |
| P3 轻微 | 不影响功能的质量问题 | 冗余代码、冲突标记残留、命名不清、日志噪声、与设计稿的细微偏差、文案措辞不统一 |

### 阶段 4：交互确认（强制环节，不可跳过）
输出问题清单后**必须停止并等待用户确认**。这是整个流程的核心闸门——在此之前一行代码都不改。用户可回复：
- 「全部修复」
- 「修复 #1、#3」（按编号指定）
- 「#2 是有意设计，忽略」

以下**高风险操作需逐项单独二次确认**，即使用户已说「全部修复」。因为这几类改动一旦出错影响面大、回滚成本高，多问一句远比事后补救划算：
- 删除任何代码（含清理冗余代码）
- 修改公共接口签名、数据库结构、配置文件
- 改动被多处调用的共享函数 / 组件

用户新增说明或修正后，更新清单再次确认，而不是直接动手。

### 阶段 5：实施修复
- **最小改动原则**：只改与 Bug 直接相关的代码，修根因而非掩盖症状。
- **不顺手重构**：不重命名、不调整无关代码结构、不统一代码风格——这些"顺手"改动会污染 diff、放大风险、让审查变难。
- **保持兼容**：不破坏接口签名与数据结构的向后兼容；确需破坏时提前说明并征得同意。
- **不擅自引入新依赖**：确有必要时先说明理由，获同意后再引入。
- 多个问题的修复尽量相互独立，便于逐项审查与回滚。

### 阶段 6：修复报告与验证建议
每项修复完成后输出：
- **改动说明**：改动的文件、关键 diff 及改动理由（改了什么、为什么这么改）。
- **影响范围**：哪些功能 / 页面 / 调用方可能受影响。
- **验证建议**：如何手动复现验证（操作步骤 + 预期结果），以及建议补充的测试用例。

## 三、冗余代码清理专项规则

删除「未使用代码」的风险高于普通修复——因为"未被引用"的判断很容易漏看动态引用，删错了就是引入新故障。因此额外遵守：

1. 删除前必须排查**动态引用**：反射调用、字符串拼接调用、路由 / 配置 / 依赖注入、构建脚本引用等。
2. 无法 100% 确认未被使用的，标注「疑似未使用」并列出排查依据，交由用户判断，不擅自删除。
3. 清理项在问题清单中单独归类（默认 P3），与功能性 Bug 分开确认。

---

## 四、边界与禁止事项

**禁止：**
- 未经确认修改任何代码。
- 将「疑似问题」当作确定 Bug 直接修复。
- 为修一个 Bug 引入大范围重构或格式化整个文件。
- 隐瞒修复带来的副作用、兼容性风险或未验证的假设。
- 静默跳过无法修复的问题（应如实说明原因与建议）。

**要求：**
- 不确定时提问优于猜测——宁可多确认一次，不可错改一行。
- 所有结论基于代码证据，引用具体文件与行号，不凭印象下判断。

---

## 五、形成更新记录

修复落地后，把本次改动写入项目根目录的 `UPDATE_LOG.md`，供后续人工或 AI 接续维护时快速了解历史改动。

- 若项目已有 `UPDATE_LOG.md`：按既有格式，将**新记录追加在最上方**（倒序，最新在前）。
- 若项目尚无 `UPDATE_LOG.md`：以本技能的 `assets/UPDATE_LOG.md` 为模板新建（各场景共用同一模板）。该模板包含使用说明、可复制的记录区块，以及一条示例记录。

每条记录严格按模板字段填写（类型、标识、背景 / 根因、改动范围、实现思路、关键决策 / 复用、依赖变更、影响与风险、测试情况、后续待办），保持格式统一，以便下一个接手的人（或 AI）能快速读懂历史。写入后与本次实际改动逐条核对，确保文档与代码一致。

> 衔接说明：若修复过程中用户要求把范围扩大到**新功能实现**（而非修复既有代码），切换到场景 A（new-feature.md）流程执行。修复完成后，项目已有交接文档集时按影响映射表联动更新受影响章节（含「已知问题」分册），并在 UPDATE_LOG 记录文档同步情况。
