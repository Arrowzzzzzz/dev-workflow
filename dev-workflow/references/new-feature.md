# 场景 A：新功能开发工作流（写代码 / 新需求 / 重构 / 优化）

> 本手册在总纲（SKILL.md）底线之上执行：确认闸门、基于证据、实施纪律、高风险二次确认、测试失败修正规则、回归测试硬门禁、自测规范均按总纲执行，本手册不再重复展开。
> 边界：**单个已定位 bug 的修复走场景 B（bug-fix.md），系统性排查走场景 C（audit-fix.md）**。用户要求测试先行时，先按场景 F（automated-testing.md）的 TDD 模式执行，再进入本流程。

【强制工作流，任何步骤不得跳过】整个过程需要不断向用户询问，只要存在任何信息不确定、不完整或未经用户确认，就不得进入下一步。禁止凭经验、习惯、假设或上下文猜测任何细节。任何实施动作都必须发生在用户确认之后；用户未确认的方案，永远只停留在讨论层。

## 阶段 1：理解现状（分析优先）

在动手之前，先充分理解相关的业务逻辑、代码实现与系统架构：

- 涉及的模块、调用链路、数据流向及关键依赖；
- 现有代码已使用的技术栈、框架、第三方库与既定编码风格；
- 该功能在整体系统中的位置与上下游影响范围；
- 若项目已有交接文档集（场景 E 产出），先查阅相关分册快速建立上下文。

禁止在未理解现有逻辑的情况下凭猜测修改代码。

## 阶段 2：澄清需求

- 厘清需求的真实目的与边界，识别隐含约束与潜在冲突；
- 带着你的理解向用户提问"这个需求到底要实现什么"，把澄清问题编号列出、一次问全，一直问到你对需求有了完整把握；
- 重构 / 优化类需求：先明确动机（解决什么痛点）与目标（如何衡量改善），再谈方案。

## 阶段 3：输出结构化实现方案

按 `assets/PLAN_TEMPLATE.md` 输出一份清晰、可评审的实现方案，至少包含：

- 需求要点总结（目的、边界、约束）；
- 改动文件清单（文件 | 改动内容 | 理由 | 风险）；
- 实现思路与关键步骤；
- **任务拆解**：大型需求拆分为多个相互独立、可单独验收的子任务清单，注明依赖顺序与每批的验收标准；
- 多种方案的对比（如有）与推荐选择及理由；
- 影响范围、风险点与兼容性考量，及回滚方式；
- 测试计划（含自测场景与回归范围推导）；
- 待确认项清单（编号）。

方案未完整输出前，不得动手实施。

## 阶段 3.5：跨角色沟通评审（实施前强制）

- 按 `references/agents.md` 第三节执行：由方案改动范围判定受影响角色 → 各角色加载自身知识库（`.devflow/agents/`）→ 按关注点矩阵依次输出评审意见 → 汇总《协作纪要》（各角色意见 + 分歧点 + 推荐裁决）；
- 协作纪要与实现方案**一并提交用户确认**；用户裁决分歧后，按裁决更新方案再进入阶段 4；
- 跨角色共识（接口契约、数据结构、测试点）写入方案的「待确认项 / 契约」，执行阶段以契约衔接。

## 阶段 4：确认后实施（关键卡点）

- 输出方案后**立即停止**，用"我想这样做：[按模板输出的方案]，是否确认？"形式主动询问；
- 未收到明确肯定（如"确认""可以""就这样"）之前，禁止以任何形式改动代码；只能继续讨论、澄清或调整方案；
- **确认粒度三档**：
  - 常规改动：整体方案一次确认后连续实施；
  - 高风险项（总纲第 4 条清单：删除代码 / 公共接口签名 / DB 结构 / 配置文件 / 共享函数与组件）：即使整体方案已确认，也逐项单独二次确认；
  - 大型需求：按阶段 3 的任务拆解分批实施，每批输出一次方案并确认，一批验收通过再进入下一批；
- 用户新增说明或修正要求后：更新方案 → 再次确认，而不是直接动手；
- 需求中途变更：回到阶段 2 / 3 重新走流程，不得在原方案上打补丁继续。

## 阶段 5：按角色与实施纪律实施

- **角色分配**：按 `references/agents.md` 第二节路由分配执行角色，加载对应角色知识文件；按 config.yaml 声明角色与模型（未配置声明平台默认）；
- 按总纲第 3 条执行：复用优先 → 最小改动 → 不顺手重构 → 保持兼容 → 新依赖先确认；加载 `references/coding-standards.md` 逐项对照检查项（强制项不满足不得宣称完成）；
- 跨角色边界不越界；越界先切换角色并说明；
- 每完成一个批次，简要小结进度并对照该批验收标准自验；
- 实施中发现与方案不符的情况（如方案假设不成立、影响面超出预期、遇到方案未覆盖的代码），立即停下向用户说明并重新确认，不自行扩大范围。

## 阶段 6：自测与回归测试（硬门禁）

- 按总纲「自测与回归规范」执行：重启判定、改动点正常/边界/异常覆盖；
- **回归测试硬门禁**（总纲第 6 条）：改动点反证 + 受影响路径回归 + 相关自动化用例全部通过，才允许宣布完成；执行细则见场景 F 手册；
- 测试失败修正按总纲第 5 条规则执行：已确认方案范围内的修正直接改并在报告中说明；超出方案范围则回到确认闸门；
- 项目无自动化测试时：列出手动验证步骤与预期结果，逐条执行并如实记录，同样必须全部通过。

## 阶段 7：形成更新记录与交接联动

- 按 `assets/UPDATE_LOG.md` 统一模板写入，新记录追加在最上方（倒序）；
- 写入后与本次实际改动逐条核对，不一致立即修正，确保文档与代码一致；
- **保鲜联动**（总纲）：项目已有交接文档集时，查影响映射表更新受影响章节；图清单表中受影响的图、`.devflow/agents/` 中受影响的角色知识文件同步增量更新，并在 UPDATE_LOG 中记录文档同步情况；
- 输出简短完成报告：改动摘要、自测与回归结果、UPDATE_LOG 所在位置；如用户随后要提交代码，提示可衔接 `git-commit-workflow` skill。

## 方案输出简例

以"新增邮箱验证码登录"为例（压缩版，完整字段见 PLAN_TEMPLATE）：

- **需求要点**：在现有密码登录之外新增邮箱验证码登录；验证码 5 分钟有效、每日每邮箱限 10 次；
- **改动文件清单**：`src/api/auth.js`——新增 `sendCode` / `loginByCode` 接口封装；`src/pages/login/index.vue`——新增验证码登录 Tab 与倒计时逻辑；
- **任务拆解**：① 后端接口对接（可独立验收）② 前端登录表单与倒计时（依赖①）③ 错误处理与文案（依赖②）；
- **影响与风险**：登录页改动影响所有登录入口；验证码接口需防刷（限流复用现有 throttle 中间件）；
- **测试计划**：接口层单测 + 登录页组件测试；回归：密码登录、验证码过期、限流三条路径；
- **待确认项**：1. 验证码发送渠道（邮件/短信）？建议邮件，短信需新供应商。
