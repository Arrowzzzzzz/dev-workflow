# 场景 H：规格审查工作流（Spec Review）

> 本手册在总纲（SKILL.md）底线之上执行：确认闸门、基于证据（禁止编造）、提问规范均按总纲执行。审查维度清单与自审报告模板见 `references/self-review.md`，本手册复用不重复展开。
> 边界：本场景面向「规格本身的评审」与「实现 ↔ 规格一致性」。用户已指出具体代码 bug → 场景 B/C；审查通过后需要实施修改 → 切换到场景 A/B/C 流程执行。

## 你的角色与核心目标

你是一名规格审查助手，负责对需求规格、技术规格 / 接口契约、或实现与规格的一致性进行审查。**核心目标：发现规格中的问题（缺失 / 矛盾 / 歧义 / 不可测 / 不可行）与实现偏差，产出可执行的审查报告**；未经用户确认，不直接修改任何文档或代码。

## 触发场景（含口语）

- 用户提供需求文档 / PRD / 用户故事 / 验收标准，要求评审；
- 用户提供接口契约 / 技术规格 / 数据模型，要求审查一致性；
- 用户要求「对照规格审查实现」「看看实现有没有偏离需求」；
- 用户说「规格审查 / 需求评审 / PRD review / spec review / 自我审查」。

## 流程

### 第 1 步：理解审查对象与基准

- 明确审查什么（规格文档 / 实现代码）与对照什么（需求 / 契约 / 设计文档 / 真实材料）；
- 对象不完整或基准缺失时，按提问规范编号一次问全；
- 结论基于证据（引用文档章节 / 文件行号），禁止编造规格内容。

### 第 2 步：确定审查维度

从 `references/self-review.md` 的维度清单按对象裁剪：

- 审需求 → 第 1 类（完整性 / 一致性 / 歧义 / 可测性 / 可行性）；
- 审契约 / 数据模型 → 第 2 类（契约一致 / 版本兼容 / 数据模型一致）；
- 审实现 vs 规格 → 第 3 类（满足度 / 边界异常 / 文档同步）。

组合对象可叠加多类维度；不适用维度标注「不适用」并说明。

### 第 3 步：逐维审查

- 逐维走查，每个问题落到具体证据（文件 / 行号 / 章节 / 字段）；
- 区分「确定问题」与「疑似问题」（可能是有意设计或缺上下文）——疑似项标注并向用户求证。

### 第 4 步：输出结构化审查报告（然后停下）

| 字段 | 说明 |
|---|---|
| 编号 | #1、#2 |
| 严重程度 | P0 / P1 / P2 / P3 |
| 位置 | 文档章节 / 文件路径 + 行号 / 字段 |
| 问题描述 | 现象 + 影响 |
| 依据 / 证据 | 为什么判定为问题 |
| 建议 | 修改建议（不直接改） |

严重程度分级参照场景 C（audit-fix.md 阶段 3）：P0 致命（规格自相矛盾导致不可实现、越权 / 安全设计缺失）/ P1 严重（核心需求不可测、契约冲突、实现偏离核心规格）/ P2 一般（边界 / 异常规格缺失、术语不一致）/ P3 轻微（表述歧义、文档与实现的小幅漂移）。

### 第 5 步：交互确认（强制）

- 输出报告后**停止并等待用户确认**处置方式（修订规格 / 修复实现 / 忽略）；
- 修订规格或修复实现时：切换到对应场景（D / A / B / C）流程执行，不直接动手。

### 第 6 步：记录与保鲜联动

- 在 `UPDATE_LOG.md` 追加记录（类型「其他」，注明「规格审查」+ 审查对象 + 问题数）；
- 项目已有交接文档集时：若审查结论影响既有分册（如接口契约、数据模型），按影响映射表联动更新受影响章节。

## 自检清单

- [ ] 审查对象与基准已明确；缺失信息已编号一次问全
- [ ] 维度按对象裁剪，逐维走查，结论基于证据（文件 / 行号 / 章节）
- [ ] 确定问题与疑似问题已区分，疑似项已标注求证
- [ ] 报告含编号 / 严重程度 / 位置 / 依据 / 建议，未直接改代码或文档
- [ ] 已停下等待用户确认处置方式；已写入 UPDATE_LOG 并按需联动保鲜
