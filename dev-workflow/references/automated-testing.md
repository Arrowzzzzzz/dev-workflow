# 场景 F：自动化测试工作流

> 本手册在总纲（SKILL.md）底线之上执行：确认闸门、基于证据、确认后动手均按总纲执行，本手册不再重复展开。
> 定位：承接独立测试任务（写测试 / 补测试 / 覆盖率 / TDD / CI 测试），同时作为场景 A/B/C 测试阶段（含回归测试硬门禁）的执行细则被引用。
> 角色：本场景任务按 `references/agents.md` 分配**测试 QA** 角色执行（加载 `.devflow/agents/qa.md` 知识库，按 config.yaml 声明角色与模型）。
> 原则：测试框架一律**先探测项目实际技术栈再适配**（Python→pytest、JS/TS→jest/vitest、Java→JUnit、Go→go test 等），不硬编码、不擅自引入新框架；引入测试依赖需先经用户同意（总纲第 3 条）。

## 一、测试策略与计划

制定策略时覆盖：

- **分层边界**：单元（函数 / 类行为）、集成（模块间、数据库、接口契约）、E2E（关键用户路径）各测什么、不测什么；
- **框架选型**：以项目现有依赖优先，确需新框架给出选型对比与推荐理由，获同意后引入；
- **优先级**：核心业务逻辑 > 易错边界（空值 / 并发 / 精度 / 时区）> 工具函数 > UI 细节；
- **覆盖率目标**：按项目现状定合理目标（建议核心模块行覆盖 ≥ 80%，关键分支必测），不与已有惯例冲突；
- 输出测试计划（表格：被测对象 | 测试层级 | 用例要点 | 优先级），经用户确认后执行；
- 输出测试计划后，先对照规格验收点做一次自我审查（见 `references/self-review.md`）——确认计划覆盖规格全部可测点，再提交用户确认。

## 二、TDD 测试先行模式（场景 A 可选前置）

用户要求测试先行时，按「红 → 绿 → 重构」循环执行，每步验收标准：

1. **红**：先写一个失败的测试，精确表达期望行为（正常路径 + 关键边界）；
2. **绿**：写最小实现让测试通过，不提前设计、不顺手扩展；
3. **重构**：测试全绿的前提下消除重复、改善结构，保持行为不变；
4. 循环直至需求完成；测试未先写，不得开始实现（用户明确豁免的除外）。

## 三、测试用例编写与执行

- **命名规范**：`test_<被测行为>_<场景>`（如 `test_login_success`、`test_login_expired_code`），断言语义清晰；
- **覆盖要求**：每个用例覆盖一个行为；正常路径 + 边界（空 / 零 / 最大值 / 超长）+ 异常（错误输入、依赖失败）；
- **断言质量**：断言行为结果而非实现细节；避免仅断言"不抛异常"；
- **隔离性**：用例间无顺序依赖、无共享可变状态；外部依赖（网络 / 时间 / 文件）用测试替身（mock / stub / fixture）；
- **执行验证**：运行测试命令（先探测项目脚本，如 `npm test` / `pytest` / `go test ./...`），全部通过才算完成；失败用例定位到具体断言并修正（修正规则按总纲第 5 条）。

## 四、覆盖率分析与补测

- 运行项目现有覆盖率工具（pytest-cov / jest --coverage / JaCoCo 等），产出覆盖率报告；
- 解读报告：按风险排序未覆盖分支（核心业务 > 异常分支 > 工具函数），输出**补测清单**（表格：文件 | 未覆盖分支 | 风险 | 建议用例）；
- 补测清单经用户确认后逐项补齐，补齐后重跑覆盖率并汇报变化。

## 五、CI 集成与运行指引

- 整理测试运行指引：本地命令、依赖安装、报告生成与查看方式；
- 失败定位方法：如何从 CI 日志 / 报告定位到具体用例与断言；
- CI 接入建议（如项目已有流水线）：测试 stage 位置、缓存、并行、覆盖率门槛；
- CI 配置的实际修改需经用户确认（配置文件属高风险项，总纲第 4 条）。

## 六、回归测试硬门禁（总纲第 6 条执行细则）

任何代码变更（场景 A/B/C 实施）完成后，按以下顺序执行，**全部通过才允许宣布任务完成**：

1. **变更影响面识别**：由方案 / 修复的影响范围列出受影响的模块与路径；
2. **回归用例选择**：优先用已有自动化用例覆盖影响面；维护「模块 ↔ 回归用例」映射清单（建议落在项目 `docs/` 或测试目录，格式见附录），无映射时先建立；
3. **改动点 / 修复点反证**：新功能按验收标准自证；bug 修复按原复现路径反证问题已消失；
4. **受影响路径回归**：逐条运行影响面对应用例；缺用例的路径**先补用例再回归**，不允许"没测试就宣称回归通过"；
5. **结果判定**：全部通过 → 写入 UPDATE_LOG、完成任务；有失败 → 按总纲第 5 条修正规则处理（范围内修正直接改并报告，范围外重新确认），修正后**从头重跑回归**；
6. 无自动化测试的项目：列出手动验证步骤 + 预期结果，逐条执行并如实记录，同样必须全部通过。

## 自检清单

- [ ] 测试框架基于项目实际技术栈选型，新依赖已获用户同意
- [ ] 测试计划已确认；用例命名规范、断言语义清晰、无顺序依赖
- [ ] 测试计划 / 用例已对照规格验收点自我审查（见 self-review.md），覆盖规格全部可测点
- [ ] 正常 / 边界 / 异常三类场景均有覆盖；TDD 模式下测试先行
- [ ] 测试与覆盖率命令实际执行过，结果真实记录
- [ ] 变更完成后回归门禁已执行：反证 + 影响面用例全部通过
- [ ] 缺用例的受影响路径已先补用例再回归，未空口宣称通过
